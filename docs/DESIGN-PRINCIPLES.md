# DESIGN-PRINCIPLES — locked UI / architecture patterns

These are decided. Extend them; re-litigate only with a DECISIONS.md entry. For KEEPER: every rule marked **DB** must be enforced in Postgres (constraint / trigger / RLS / transition function); the UI merely previews it.

| # | pattern | rule | prototype location | KEEPER enforcement |
|---|---|---|---|---|
| 1 | **One data module** | Screens never fetch, never touch storage, never hold their own fixtures. Everything goes through typed functions in `src/api/client.ts`; fixtures under `src/api/fixtures/`. Repointing = one file. | `client.ts`, `fixtures/` | Same module shape over Supabase RPC; screens unchanged |
| 2 | **Pipeline on one page** | A module's whole flow is visible **left → right on one screen** with a **live count per stage**: Intake 4 tabs; Jobs board 9 lanes (incl. On hold); Floor Map 9 lanes; Estimates status chips; SO tail pills. Queues are **work lists** (Bench, Supervisor, Pickup/Ship Station, Inbox), not dashboards. Holds are **flagged in-lane** (On hold lane / hold pill), never hidden. The **sidebar moves between machines, never through one** — no wizard that hides the map. | `IntakeLayout`, `JobBoard`, `FloorMapPage`, `EstimatesListPage`, `Sidebar` | Lane counts = views over status tables |
| 3 | **Only legal actions render** | Next steps come from the state machine (`legalJobActions`, estimate/SO status checks). Buttons, never a status `<select>`. Held jobs render zero transitions. Required reasons are declared on the action, enforced in the module. Disabled + explanation strip when a gate blocks (`ReviewGate`). | `JOB_ACTIONS`, `transitionJob`, `reviewGaps`, `EstimateDetailPage`, `SalesOrderDetailPage` | **DB**: `transition_job(job_id, action, reason)` validates from/to, reason, gates; `status` column not writable by clients |
| 4 | **Label at point of work** | Capture where the truth is known, in one tap: scan-first inputs auto-focus + Enter; **pre-filled candidates** (estimate scan pre-fills client/contents; Receive Watch pre-populates from estimate; parts assistant suggests part numbers; `@mention` autocomplete); **one-tap confirm / override** (content pills, same-watch fork returning/conflict, workflow picker, QC pass/fail); **in-workflow prompts** (discrepancy list live, review-gate strip, unpaid bypass field); **automatic provenance** (labels queue at Receive Watch; approving a parts request records the requester's own words as aliases; quick-add attaches the record you're on). | `ArrivalPage`, `ReceiveWatchPage`, `PhotoCapture`, `PartsChat`, `QuickAddOverlay` | Provenance columns (`source_request_id`, `via`) not nullable where the prototype fills them |
| 5 | **Audit-stamp everything** | Every mutation appends an `AuditEvent {type, who, station, when, detail}` and the record itself carries `Stamp {at, by, station}` (transitions, holds, notes, photos, shop time, payments, shipment, pickup, tasks, pins). Failed sign-ins and bypasses are logged. Portal writes are stamped as the client + station "RolliConnect". | `appendAudit`, `*Stamp` helpers, `asClient` | **DB**: `created_by/created_at/station_id` NOT NULL via `auth.uid()` + session station; append-only transition/audit tables (no UPDATE/DELETE grants) |
| 6 | **Role-based routing and ownership** | Accountability attaches to a **role**, resolved to holders at read time (`roleHolders`). `Job.owner: Role` (one accountable) ≠ `Job.assignees: string[]` (many working). Tasks/pins target a user **or** a role. `/today` is **derived** from these plus a manual pinned layer. Tier (`manager/concierge`) gates visibility only; **division** (`rolliworks/rollishop`) is the wall — sessions inherit the station's division; hit lists, pickers and staff viewer never cross it, even for managers. | `User.roles`, `Job.owner`, `Assignee`, `getToday`, `getDivisionStaff/Roles` | **DB**: `user_role` join table; `job.owner_role` FK to `role`; RLS on division for today/tasks/pins; `check (assignee_user_id is null) <> (assignee_role is null)` |
| 7 | **Lookup tables, not enums** | Behaviour per kind / status / dept / reason is a **data table the UI reads**: `JOB_KIND_CONFIG`, `JOB_ACTIONS`, `INSPECTION_QUESTIONS`, `WATCH_STATUS_FOR`, `EMAIL_FOR`, `DEPT_LABEL`, `DEPT_COMPONENTS`, `PORTAL_STATUS`, `REQUEST_CLOSE_REASONS`, `FLOOR_LANES`, `BINS`, `CONTENT_PILLS`, `CARRIERS`. Adding a kind, stage, question or reason = adding a row. **No Postgres enums.** | `client.ts`, `fixtures/intake.ts` | Lookup tables with FK; `job_kind` seeded `service, warranty, small_job` (+ planned `rehab, internal`) |
| 8 | **Enum-plus-note for forced reasons** | Where a reason is mandatory it is a **picked code + free note**, never free text alone: request close (`duplicate \| no_longer_needed \| mistake` + note, `duplicate` requires a target), hold type + reason, QC fail reason, payment bypass reason, admin-mark note, cancel reason, decline reason. | `REQUEST_CLOSE_REASONS`, `placeHold`, `qc_fail`, `confirmPickup/Shipment` | `reason_code` FK + `reason_note text`; CHECK non-empty where the prototype throws |
| 9 | **Pack wins, brief second, UNKNOWN → simplest + amber** | Legacy prompt packs override the session brief on fields, statuses, rules. Anything the pack marks UNKNOWN is built the simplest way and tagged `<Provisional/>` in the UI and "provisional" in docs. | `Provisional` component, `PROMPT-PACK-*.md` | Provisional rows called out in DECISIONS |
| 10 | **Outbox, never send; no real money** | Client emails are queued as `OutboxEmail` with full body; nothing leaves the app. Money is display arithmetic; tax shown "not applied"; QBO, payments, carrier are stubs with visible state. | `store.outbox`, `totalsFor`, `shippingProvider` | Outbox table + worker; same body templates |
| 11 | **Routing authority = Receive Watch** | The workflow set (W/B/P/PM) recorded at intake stage 4 governs the job; jobs inherit it from the received package before falling back to line depts. | `receiveWatch`, `jobFromEstimate` | Trigger on job insert copies `package.workflow` |
| 12 | **Naming: "PM" = precious metals** | `PM` is a `DeptCode` only. Accountability is always `owner`; techs are `assignees`. Never "PM" for project manager in schema, UI or docs. | `types.ts`, `OwnerBadge` | Column names `owner_role`, `assignees` |
| 13 | **Derived first, pinned on top** | If a list can be computed from state (hit list rows, lane counts, KPIs, waiting-on, custody, tail stage, portal status, Client 360) — compute it. Explicit items are stored only as tasks and pinned items; pins sit in their own section above derived rows and **never hide them**. | `getToday`, `pinToHitList`, `tailStage`, `custodyOf`, `portalStatusFor` | Views / RPC; no stored duplicates of derivable state |
| 14 | **Evidence before advance** | Leaving review requires inspection photos for every kind; the multiple-choice report only where the kind's config says so. Gates live in the module (`reviewGaps`); the UI reflects them. Custody closes only with hand-back photos (pickup / ship). | `JOB_KIND_CONFIG`, `reviewGaps`, `confirmPickup/Shipment` | **DB**: transition function checks photo counts / report row |
| 15 | **Lenses, not modules** | Bench, Supervisor and Floor Map read the same job store through role-shaped views; they add no statuses. Learning loops (parts) write to lookup tables (`compatibleRefs`, `aliases`) and a visible knowledge log, never hidden state. | `getBenchView`, `getSupervisorBoard`, `getShopFloorMap`, `approvePartsRequest` | Views; `part_alias` / `part_reference` tables + knowledge log |
| 16 | **One box answers the phone** | Any identifier a caller can read out resolves through `resolveIdentifier` to the client's 360 page with the matched row flashed (`?hit=`). New record types register in the resolver (kind + hitKey) and carry `data-hit`. | `resolveIdentifier`, `Client360Page` | Search RPC over the same identifier set |
| 17 | **The portal is a different product on the same store** | `/rc` has its own shell, session, palette and vocabulary (status words, no percents, no ERP nouns); never links to staff routes. Client writes go through the **same functions staff use**, stamped as the client, audited as `portal`; an approval in the portal advances the linked job. | `RcShell`, `asClient`, `PORTAL_STATUS` | Separate Supabase role/RLS (client sees own rows); same transition functions |
| 18 | **Global quick-add, anywhere** | One-line capture from any screen (`＋` / `Alt+T`); `@name` / `@role` routes to that list, plain text pins to self; the current record (job / client / estimate) is attached automatically; autocomplete is division-scoped. | `QuickAddOverlay`, `parsePin`, `pinToHitList` | Same RPC; mention resolution server-side |
| 19 | **Dense, keyboard-first staff UI** | Tight spacing, mono for ids, Enter submits, ⌘/Ctrl+Enter confirms modals, rows focusable, auto-focus the scan/search field, `data-testid` on every interactive/critical element. | all staff pages | — |

## Anti-patterns (don't)
- Free status `<select>`; `UPDATE … SET status` from a screen or an API without the transition function.
- New storage paths, `fetch`, component-local fixtures, or a second copy of derivable state.
- Postgres `ENUM` types for anything a manager might add a row to.
- A "PM" / project-manager field.
- Subtasks, task kanban, comments, priority schemes on tasks (out of scope by decision).
- Hiding or filtering derived `/today` rows because something was pinned.
- Silent dead buttons — a stub must throw a visible message and be audited.
- Percent / progress bars or internal status enums in RolliConnect; links from `/rc` into staff routes.
- Cross-division visibility "because they're a manager".
